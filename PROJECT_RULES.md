## 4.2. Позиционные настройки

### positionPrecision (точность координат)
- Настройка **КАНАЛА** (`ChannelSettings.ModuleSettings.position_precision`), НЕ позиции!
- 0 = не передавать, **13 = дефолт прошивки (~2.9км)**, **32 = максимальная (~1м)**
- CLI: `meshtastic --ch-index 0 --ch-set module_settings.position_precision 32`
- ⚠️ НЕ `--set position.position_precision` (устаревший/неверный путь!)

### positionFlags (состав данных позиции)
- Битовая маска `position.position_flags` (protobuf Config.PositionConfig)
- ALTITUDE=1, ALT_MSL=2, GEO=4, DOP=8, HVDOP=16, SAT=32, SEQ=64, TS=128, HEADING=256, SPEED=512
- **Дефолт прошивки**: 811 = ALT+MSL+DOP+SAT+HEADING+SPEED (транспорт)
- **Наш дефолт (пеший)**: 299 = ALT+MSL+DOP+SAT+HEADING (без SPEED)
- Все флаги: 1023
- ⚠️ SPEED/HEADING — для транспорта, пешком ненадёжны

### fixedPosition (фиксированная позиция)
- `position.fixed_position` (protobuf Config.PositionConfig, поле 3)
- **true** = устройство использует последнюю известную позицию без обновления от GPS
- Для стационарных устройств: базовая станция, трекер в лагере
- ⚠️ **Баг прошивки #8403**: если GPS включён (ENABLED), коллбек `onGPSChanged` перезаписывает fixed_position! Поэтому при `fixed_position=true` мост принудительно ставит `gps_mode=DISABLED`
- CLI: `meshtastic --set position.fixed_position true`
- Для задания конкретных координат: `meshtastic --setlat XX.XXXX --setlon YY.YYYY --setalt ZZ`
- Python API: `node.setFixedPosition(lat, lon, alt)` или `node.removeFixedPosition()`
- ⚠️ При `fixed_position=true` и `position_precision < 32` — координаты округляются и повреждяются (баг #7478)

### ⚠️ Проблема: дрейф GPS координат у стационарного трекера

**Симптомы**: трекер стоит на месте, но координаты прыгают (±5-50м). После перезагрузки работает корректно некоторое время, затем начинает дрейфовать.

**Причины (от наиболее вероятной к наименее)**:

1. **Аппаратный дефект T-Echo (LilyGO #32)** — внутри устройства полоска проводящей сетки (conductive mesh tape) соединяет землю SMA-разъёма с экраном GPS-чипа. На некоторых экземплярах эта сетка замыкает пассивные компоненты правее гнезда GPS-антенны, нарушая работу L76K GNSS-приёмника. Симптом: GPS получает фикс при включении, но через несколько минут счётчик спутников падает до 0. **Решение: вскрыть корпус, переставить изолирующую ленту под проводящую сетку** (подробности: https://github.com/Xinyuan-LilyGO/T-Echo/issues/32)

2. **Баг #836 — T-Echo теряет GPS-фикс** — даже без аппаратного дефекта, T-Echo (L76K GNSS) периодически теряет спутники после нескольких минут работы. После перезагрузки GPS снова работает, но затем деградирует. Это подтверждённый баг прошивки, специфичный для T-Echo/nRF52840.

3. **Слишком частый GPS-опрос** (`gpsUpdateInterval` < 30 сек) — L76K GNSS не успевает получить качественный фикс за 1-10 секунд, особенно в лесу. Результат — «сырые» неточные координаты с высоким HDOP. Дефолт прошивки: 0 (= 120 сек), что даёт GPS время на полный TTFF и качественный фикс.

4. **Естественный шум GPS** — потребительский GPS имеет погрешность ±3-10м даже неподвижно (спутниковая геометрия, атмосфера, переотражения). Meshtastic **не фильтрует/сглаживает** GPS — каждый «сырой» фикс используется напрямую.

5. **Умное вещание (smart broadcast)** с малым `smartBroadcastMinDist` (20м) — колебания GPS могут превысить порог, вызывая ненужные вещания с разными координатами. Дефолт прошивки: 0 (= 100м).

6. **position_precision < 32** — обфускация координат для приватности ИСКУССТВЕННО сдвигает координаты при каждом вещании (выглядит как дрейф).

**Решения**:

| Решение | Когда применять | Настройка |
|---------|----------------|-----------|
| 🔧 Проверить аппаратный дефект | T-Echo теряет спутники через 2-5 мин | Вскрыть корпус, переставить изолирующую ленту (LilyGO #32) |
| Увеличить `gpsUpdateInterval` | GPS не успевает дать точный фикс | **30 сек** минимум (дефолт прошивки = 120 сек) |
| Увеличить `smartBroadcastMinDist` | Трекер в лесу, много ложных вещаний | **100м** (дефолт прошивки) вместо 20м |
| Включить `fixedPosition` | Трекер стационарен (лагерь, база) | `fixedPosition=true`, GPS→DISABLED |
| Установить `positionPrecision=32` | Координаты «прыгают» на км | Уже установлено в наших пресетах |
| Задать координаты вручную | Базовая станция в помещении | `--setlat` / `--setlon` / `--setalt` |
| Отключить smart broadcast | Стационарный трекер + дрейф | `position_broadcast_smart_enabled=false` |

**Рекомендуемые настройки для подвижного трекера (лес)**:
```bash
meshtastic --set position.gps_update_interval 30 \
           --set position.position_broadcast_smart_enabled true \
           --set position.broadcast_smart_minimum_distance 100 \
           --set position.broadcast_smart_minimum_interval_secs 300 \
           --set position.position_broadcast_secs 300
```

**Рекомендуемые настройки для стационарного трекера**:
```bash
meshtastic --set position.fixed_position true \
           --set position.gps_mode DISABLED \
           --set position.position_broadcast_smart_enabled false \
           --set position.position_broadcast_secs 3600
```

**Сравнение пресетов с дефолтами прошивки**:

| Параметр | Дефолт прошивки | Трекер 12ч (было) | Трекер 5д | Рекомендация |
|----------|----------------|-------------------|-----------|--------------|
| gpsUpdateInterval | 0 (=120 сек) | 1 сек ❌ | 30 сек ✓ | ≥30 сек |
| positionBroadcastSecs | 0 (=900 сек) | 60 сек | 300 сек ✓ | 300 сек |
| smartBroadcastMinDist | 0 (=100 м) | 20 м ❌ | 50 м | 100 м |
| smartBroadcastMinInterval | 0 (=900 сек) | 60 сек | 300 сек ✓ | 300 сек |
| positionPrecision | 13 (~2.9 км) | 32 ✓ | 32 ✓ | 32 |

**Известные баги прошивки**:
- **#836**: T-Echo GPS теряет фикс через несколько минут (счётчик спутников → 0). Возможная аппаратная причина: LilyGO #32 (проводящая сетка замыкает GPS-антенну). Без аппаратного фикса — использовать `fixedPosition=true` для стационарных устройств
- **#8403**: `onGPSChanged` перезаписывает fixed_position → решение: gps_mode=DISABLED
- **#7478**: position_precision < 32 округляет и повреждяет fixed coordinates → решение: position_precision=32
- **#8029**: GPS lock hold 20 сек — при интервалах < 20 сек возможны циклы обновления
- **#992**: T-Echo GPS знак координат инвертируется (редко, но возможно)
- **#6785**: Smart Position Broadcast не всегда соблюдает интервалы — спорадическое вещание у стационарных устройств

## 4.3. Телеметрия (данные от трекера)

Мост извлекает данные из protobuf-пакетов Meshtastic и отправляет в дашборд:

### Position (порт 3)
| Поле protobuf | Поле БД | Конвертация | Описание |
|---------------|---------|-------------|----------|
| latitudeI | latitude | ÷ 1e7 | Широта |
| longitudeI | longitude | ÷ 1e7 | Долгота |
| altitude | altitude | как есть | Высота (м) |
| groundSpeed | speed | ÷ 1000 мм/с → м/с | Скорость |
| groundTrack | heading | ÷ 10000 → градусы | Курс |
| satsInView | satsInView | как есть | Кол-во спутников GPS |
| HDOP | hdop | ÷ 100 | Горизонтальная точность |

### DeviceMetrics (порт 7, телеметрия)
| Поле protobuf | Поле БД | Описание |
|---------------|---------|----------|
| batteryLevel | batteryLevel | Заряд батареи (%) |
| voltage | voltage | Напряжение (В) |
| channelUtilization | channelUtilization | Загрузка канала (%) |
| airUtilTx | airUtilTx | Использование эфира TX (%) |

### EnvironmentMetrics (порт 7, телеметрия)
| Поле protobuf | Поле БД | Описание |
|---------------|---------|----------|
| temperature | temperature | Температура (°C) |
| humidity | humidity | Влажность (%) |
| barometricPressure | pressure | Давление (гПа) |

⚠️ Мост использует кэши `node_dev_metrics` и `node_env_metrics` для передачи этих данных в periodic sync (раньше они терялись — извлекались в on_receive, но не попадали в node_entry).

### Определение USB/внешнего питания

usbPower определяется по **трём критериям** (любой из них):
1. Прямое поле `usbPower` из DeviceMetrics (если прошивка его передаёт)
2. `batteryLevel >= 101` — Meshtastic шлёт 101% при USB-питании
3. `voltage >= 4.4V` — гарантированно внешнее питание (LiPo максимум 4.2V)

⚠️ batteryLevel=101 от прошивки обрезается до 100 через Math.min() при сохранении в БД (101→100). Мост больше не обрезает — сохраняет 101 как маркер для логики usbPower.

## 4.3.1. Имя устройства (setOwner / factory reset)

### Как правильно менять имя устройства
- **Через дашборд**: Диалог редактирования узла (карандаш) → ввести имя → включить «Установить на устройстве» → Сохранить. Вызывает `POST /api/meshtastic/set-owner` → мост → `setOwner()`.
- **Через пресеты**: Вкладка «Пресеты» → выбрать пресет → ввести имя → «Загрузить на устройство». Вызывает `setOwner()` + применяет весь пресет.
- **Через CLI**: `meshtastic --set-owner "Имя" --set-owner-short "IMYA"`
- ⚠️ **Без опции «Установить на устройстве»** имя меняется ТОЛЬКО в БД дашборда и будет перезаписано при следующей синхронизации с устройством!

### API моста: POST /api/set-owner
- Параметры: `nodeId` (hex `!a1b2c3d4` или пустая строка для BASE), `deviceName`, `deviceShortName`
- Вызывает `setOwner()` на целевом узле (локальном или удалённом через mesh)
- `ensureSessionKey()` вызывается перед `setOwner()` — обязательно для 2.7.x
- Не требует перезагрузки устройства — имя обновляется сразу
- Дашборд обновляет БД при успехе

### Ограничения Python-библиотеки meshtastic 2.7.8
- **short_name макс. 4 символа** (nChars=4 в setOwner()), НЕ 5! Протокол позволяет больше, но библиотека обрезает.
- **Пустая строка вызывает sys.exit()** — мост падает! Поэтому пустые строки конвертируются в None (пропуск setOwner).
- `setOwner()` вызывает `ensureSessionKey()` внутри себя — не нужно вызывать отдельно перед ним.

### Factory reset и имя
- `factory_reset_config` (поле 99 в AdminMessage) → `nodeDB->factoryReset()` → `installDefaultDeviceState()` → имя сбрасывается на «Meshtastic XXXX»
- `factory_reset_device` (поле 94) → то же + очистка BLE bonds
- ⚠️ После factory reset мост вызывает `setOwner()` — если поля имени заполнены старым именем, оно перезапишет дефолтное!
- **Решение**: при включении factory reset поля имени очищаются автоматически. Пользователь может ввести новое имя или оставить пустым для дефолтного.
- Проверено по исходникам AdminModule.cpp + NodeDB.cpp прошивки 2.7.15

## 4.3.2. Автоопределение offline-узлов

- `GET /api/nodes` автоматически определяет статус узла по полю `lastSeen`
- Если `lastSeen` старше **15 минут** — узел переводится в `status=offline`
- Это серверная логика: при каждом запросе списка узлов проверяется `now - lastSeen > 15 мин`
- Условие: трекер шлёт пакеты каждые ~70 сек → 15 мин без пакетов = гарантированно не на связи

## 4.4. Mesh-стратегия

- **Трекеры (TRACKER)** — конечные узлы, спят и экономят батарею, не ретранслируют пока спят
- **Надёжность mesh обеспечивается промежуточными узлами** (ROUTER / REPEATER), не трекерами
- При развёртывании в лесу — планировать размещение ROUTER/REPEATER между базой и трекерами
- Каждый промежуточный узел сокращает дистанцию прыжка → надёжнее через лес
- ROUTER — видимый backbone, всегда бодрствует, пакеты предпочитают маршрут через него
- REPEATER — невидимый ретранслятор, ноль overhead, чистая пересылка, идеален для дешёвых узлов на деревьях
- Рекомендуемый модем-пресет для леса: **LONG_MODERATE** (все узлы должны использовать одинаковый)
- hop_limit = 5-7 для леса (дефолт 3 — мало для пересечённой местности)
- Мокрая листва = -30..50% дальности → закладывать запас по количеству промежуточных узлов
